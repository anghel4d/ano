# ano ECS — the column store beneath the language

Status: replacement design, 2026-07-15. Steel and Kore are the only live implementations. This document is the storage and typed-IR contract they must grow into; it is not a C implementation plan and no C tree is an oracle.

## 0. Position

Ano is a resident query-and-command language over a columnar world. The host may use archetypes, sparse sets, AoS, another database, or no ECS at all. Registration maps host state into Ano habitats and columns. Ano's semantics never depends on the host's physical layout.

The store's central invariant is alignment: every buffer is indexed by a declared domain, every derived view carries lineage back to its sources, and every write carries a destination map back to a stored habitat. Contiguous memory is the implementation of this invariant, not its replacement.

The formal definitions are in `proofs/foundations.md`. This note gives them a machine shape.

## 1. World schema

A schema `Σ` declares nominal habitats and frames, point and vector carriers, components, relationships, fields, functions, merge families, authorized lineage declarations, situated capabilities, placements, locators, interpolators, and support projectors. A world value inhabits `World Σ`.

The live entity population is a nominal habitat whose membership may change. A lattice field habitat is fixed by its declaration. Spawn and despawn change a world value but do not change `Σ`; a field update changes values but does not change its habitat, rank, or shape.

An ECS component over entity habitat `E` is a partial column: a presence bitmap plus values. A dense field over fixed habitat `D` is total. An opaque handle column is ordinary column storage with a carrier whose admitted operations come only from the registry.

A position component is still a partial entity column, but its carrier is `Point<F>` for one nominal frame `F`; the component name and a three-number item shape confer no frame. `Point<F>`, `Vector<F>`, `CellRef<H>`, entity keys, and physical row offsets remain distinct carrier types even when their buffers share one machine representation.

## 2. The physical descriptor

The next Steel IR needs an object equivalent to:

```rust
struct Domain {
    habitat: HabitatId,
    rows: usize,
    rank: usize,
    shape: Vec<usize>,
    layout: LayoutId,
}

struct Column {
    domain: DomainId,
    carrier: CarrierId,
    item_shape: Vec<usize>,
    values: BufferId,
    validity: Option<BitmapId>,
}
```

`rank` and `shape` describe the row domain. `item_shape` describes one value. A 64×64 scalar height field has row shape `[64,64]` and empty item shape. A 64×64 world-position field with 3-vectors has the same row shape and item shape `[3]`.

Entity columns may share a physical slot layout while remaining logically partial through their presence bitmaps. Lattice fields may share one habitat and layout. Buffers on different habitat IDs never combine merely because `rows` agrees.

## 3. Query domains and lineage

Every plan operates over a current row domain `X`. It carries one lineage map for each bound source role:

```rust
struct View {
    domain: DomainId,
    lineage: Vec<(SourceRole, IndexMap)>,
    order: Option<OrderId>,
}
```

A selection uses an inclusion map. A relationship hop adds a partial target map. A comprehension product carries two projections. Replication carries the copy-to-source projection. An ordered pipeline keeps the same rows and attaches an order. These maps are usually integer vectors or affine descriptors and may fuse away before execution.

The type of a computed expression is `Col<X,V>`. Pointwise kernels take operands over the same `X`; scalars broadcast explicitly. Any other combination first performs a registry-authorized reindexing and retains its provenance in the plan. Authorization is generated by selection, product, replication, declared relation legs, typed cell-reference reads, or a declared spatial bridge; it is never generated by equal length, equal shape, an arbitrary function, or a physical layout. This makes a cross-habitat expression a type error instead of a delayed BQN length accident.

Frame maps transform point or vector values covariantly. Placement maps habitat sites to framed points. Neither is an `IndexMap` or row lineage, so neither can scatter values back into a habitat without a separately registered locator, interpolator, cell-reference relation, or destination map.

## 4. Columnar execution

The formal operations lower without row objects:

| semantic operation | physical operation |
|---|---|
| presence and predicate | bitmap algebra and vector compare |
| selection restriction | bitmap plus optional compression |
| pullback | gather by index vector |
| relationship image | bitmap scatter-OR |
| grouped fold | segmented reduce or scatter-reduce |
| outer product | product index arithmetic and paired lineage |
| replicate | counts, prefix sum, repeated source indices |
| ordered view | permutation vector |
| scan | dense scan in the declared order |
| effect | destination vector, values, validity, merge family |

Compression creates scratch storage over a derived domain `S`; it never turns `S` into the target habitat. Scatter uses the saved inclusion or destination vector to return values. The hot path remains masks, contiguous arrays, gathers, reductions, and scatters.

## 5. Relationships

A relationship is a typed span `I ← R → J`. Its declaration names both endpoint habitats. Three useful physical forms remain:

- Functional or partial-functional: one target key per source row plus validity.
- Set-valued: CSR offsets plus target keys.
- Implicit: a generated edge relation such as a lattice stencil.

A functional hop gathers a target column and intersects validity with link liveness and target-component presence. A set hop produces an edge/fiber view. The image reduces targets by Boolean OR. γ reduces edge-aligned values along a relationship leg using the requested fold.

Keys are not untyped numbers in the IR. An entity key, a lattice coordinate, and a row offset have distinct types even if all lower to integers. A stored relation may cross habitats only if its declared endpoints say so.

## 6. The barrier

A statement gathers against one pre-state and produces an effect buffer. Each effect record contains:

```rust
struct Effect {
    target: ColumnId,
    destinations: IndexMap,
    values: Column,
    merge: MergeFamily,
}
```

Commit groups effect rows by destination. Assignment requires injective destinations or a deterministic conflict certificate. Add, minimum, maximum, Boolean OR, and similar collision-tolerant effects reduce each destination fiber with their registered commutative monoid. The effect buffer is therefore a columnar relation from query rows to target rows, not a list of entity callbacks.

Every stored target preserves its domain through a value barrier. This law applies equally to entity components and lattice fields. A rank-changing expression may feed another expression, but it cannot overwrite a field on a different domain.

## 7. Allocation

For selected sources `S` and counts `c : S → Nat`, the copy domain is `C = Σ(s:S).Fin(c(s))`. A prefix sum allocates its contiguous rows; a repeated-source index vector implements the projection `C → S`.

Spawn then allocates fresh keys `C ↪ E'`, pulls source values to `C`, fills proto/default columns, and appends the new entity columns. Canonical source order plus copy index gives deterministic allocation.

An entity-valued `parent` column may be filled from the source projection only when the source has entity lineage. A cell of `Ground` is not an entity parent. Spawning from a lattice may fill a position through a registered placement, or a separately typed cell-reference relationship, but it may not store the flat cell offset in an entity relationship by coincidence.

An exact spatial spawn resolves every source and proposal against the same frozen pre-state. The phrase “the player” therefore requires exactly one source row or refusal. Its 51-copy domain is `Fin(51)`; a general source habitat `X` gives `Σ(x:X).Fin(51)` and means 51 per source. Every copy retains source and copy index, crosses frames only through registered frame maps, and obtains support only through the registered projector.

All required hits and collider-aware resting poses validate before allocation. Success uses one shared injective copy-to-entity allocation for every spawned component and creates the whole copy domain. A missing hit, unresolved deterministic choice, invalid resting pose, or allocation refusal returns the exact input world and allocates no prefix. Fresh destination keys prevent component-write collisions; geometric overlap between distinct fresh entities remains a separate optional clearance validation.

## 8. Spatial fields

A lattice declaration supplies a nominal habitat identity `H`, site type `D_H`, rank, shape, product presentation `Box(shape_H) ≅ D_H`, chart, and bounded lookup. Equal rank and shape do not identify habitats or authorize a map between them. A field declaration names that exact habitat and a carrier. Frame, placement, locator, interpolation, support projection, metric, stencil, and boundary are independent capabilities.

Conceptually:

```text
lattice ground shape 64 64
field Water on ground bool
field Height on ground num

affine world3 dim 3
frame ground in world3
  origin 100 0 200
  basis 1 0 0 | 0 0 1
```

The first three lines suffice for an unplaced field. The frame maps ground coordinates into a separately declared 3-D affine parent. Registry spelling is not yet ruled; the semantic separation is.

A nominal frame `F` supplies distinct `Point<F>` and `Vector<F>` carriers plus the admitted affine operations. `Position<World3>` means that the item carrier is a point in `World3`; the column remains indexed by its entity presence habitat. Equal coordinate dimension, axes, or units do not identify frames.

A placement has semantic type `D_H → Point<F>` and transforms values covariantly. It does not reindex the field, is not required to be injective or invertible, and never derives a locator. A `situated(H,F)` declaration is the registry evidence that binds the exact habitat and frame and names the placement plus whichever return bridges are actually admitted.

A locator has type `Point<F> ⇀ D_H` and certifies one declared single-valued choice relation. An interpolator returns a finite typed support in `D_H`. A frame map relates exact nominal frames. These declarations, registered lineage, and typed relationships are the only bridges by which a position-bearing entity column can orient around or sample a field habitat. Physical layouts and structural equality of descriptors provide no such bridge.

A support projector reads one frozen snapshot and returns either a typed surface hit or explicit failure. A successful hit must satisfy the registered `Best` predicate: incidence, ray and interval, admissible normal, minimum semantic cost, and a deterministic semantic tie key. Candidate enumeration and buffer order are forbidden tie policies. The hit is a contact point; a prototype's `RestingPose` or support offset converts it to an entity origin before the position effect is admitted.

```text
Position<World3> on Entities + locateGround : Point<World3> ⇀ CellRef<Ground>   accepted
Position<MarsLocal> at locateGround                                                rejected: foreign frame
Height on Ground + Height on MarsSurface                                           rejected: equal shape is not alignment
layoutRow as CellRef<Ground>                                                       rejected: physical order is not lineage
placement(Ground,World3) used backward                                             rejected without a registered locator
```

The current singleton `lattice w h` header is insufficient because it leaves the habitat unnamed, restricts rank to two, gives every field one accidental domain, and cannot type more than one lattice. The replacement must permit multiple named habitats and arbitrary finite rank without making geometry mandatory.

## 9. Stencils and boundaries

A stencil is an implicit relationship on a lattice habitat. Its displacement set is evaluated against the lattice chart. Boundary behavior belongs to the relationship or field operation and is saved as schema:

- shrink removes out-of-window edges;
- constant extends the value outside the window;
- clamp and reflect map attempted coordinates back into the window;
- wrap uses modular coordinates and gives the habitat toroidal structure.

Current Steel implements every `neighbor` spelling as one hard-coded clamp helper and ignores the distinction. Explicit stored `srel` fibers, such as Conway's `moore`, work because they bypass that helper and carry the edge relation extensionally.

## 10. Host boundary

Registration maps host data to typed columns. Zero-copy is legal when the host layout matches the declared habitat layout and remains stable for the tick. Otherwise ingest gathers or transposes into Ano-owned buffers. Either path produces the same typed column descriptor.

Readonly host columns have no write capability. Host functions receive typed views and return typed columns or effect buffers with declared footprints. Opaque handles remain opaque because no native carrier operation is registered, not because their bytes live outside the column store.

Registration of a spatial bridge supplies both executable host behavior and the witness required by its semantic contract. A host locator or projector returning an in-frame index is not accepted merely because that index is in bounds; its plan node names the exact habitat, frame, frozen snapshot dependency, choice law, and failure behavior. This contract describes the registry boundary Steel and Kore must grow into; it does not claim that either currently constructs these certificates.

## 11. Tick and persistence

A tick is `World Σ → Result(World Σ × Output)`. Rules gather one pre-state and share one rule barrier; queued commands follow in program order. Spatial localization, support choice, resting-pose validation, and every ordinary read in one statement observe that same frozen pre-state. An exact structural effect validates its whole proposal domain before allocation. A refused statement returns the input world extensionally unchanged and commits neither values nor fresh identities.

Save and reload must preserve schema identity, habitat and frame declarations, layouts, field rank and shape, point and vector carrier frames, authorized relationship and spatial-bridge endpoints, placement and locator identities, support policy and semantic tie identity, boundary forms, and live nominal keys. Persisting only flat values plus a global width and height is not sufficient.

Repeated execution is a type invariant: a program accepted at tick zero must have the same domain derivation at tick one regardless of entity population growth. Computed-line and spatial-top-k currently violate this because their temporary numeric frames are not stored in the IR.

## 12. Steel migration order

1. Add `HabitatId`, row-domain descriptors, item shape, and validity to the resolved IR.
2. Make registry columns declare a habitat; convert the current entity world and singleton lattice into explicit declarations during loading.
3. Give every expression and mask a query-domain ID; reject foreign pointwise operands.
4. Replace `Mode::{World,Sel,Copy}` with explicit reindex maps over view domains.
5. Lower effects through destination maps and merge families.
6. Add named arbitrary-rank lattice habitats, nominal frames and `Point<Frame>` carriers, then certificate-bearing frame maps, situated placements, locators, interpolators, and support projectors.
7. Rebuild the spatial demos as repeated-tick Steel/Kore tests. BQN may remain an exploratory backend language, never the semantic oracle.

The first useful vertical slice is one entity component, one 2-D field of the same length, and a refusal proving that they cannot combine without an explicit map. The success case is a masked field update followed by save, reload, and a second identical tick with rank and shape unchanged.
